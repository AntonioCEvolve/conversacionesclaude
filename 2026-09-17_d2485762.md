## 4. Datos oficiales del post "How to use Mobbin MCP: data from 317,427 queries" `[oficial-indirecto]`

**Advertencia de método:** `mobbin.com` bloquea el acceso (403). Todo lo siguiente proviene de fragmentos del post indexados por el buscador. Los números son citas del post oficial, pero **no he podido leerlo entero ni verificar la lista completa de 30 prompts**.
URL: https://mobbin.com/blog/how-to-use-mobbin-mcp

**Volumen (primer mes):** 10.105 personas conectaron el MCP; 317.427 consultas.

**El hallazgo central — nadie lo usa para generar:**
- Solo **16 consultas** de 317.427 decían "generate me UI".
- *"Not one of the top 50 searches contains the word 'generate'."*
- Prompts generativos tipo *"design me a fintech app and make it not suck"* **no aparecen** en el top.
- Conclusión oficial: *"People are using it the way designers always have: to look things up."*

**Qué se busca:**
- Nº 1: **"login screen"** (319 usuarios distintos). Después: onboarding welcome screen, dashboard, settings screen, pricing page, empty state, checkout flow.
- **Onboarding + dashboards + paywalls ≈ 30%** de todas las consultas. El resto: navegación, formularios, checkout, interfaces de chat, empty states.
- **Interfaces de IA/LLM = segunda categoría más buscada** (comparar ChatGPT, Claude y Perplexity: UI de conversación, indicadores de "pensando", visualización de uso de herramientas).

**Especificidad:**
- **15%** de las consultas nombran una app concreta; **85%** son patrones genéricos.
- Cuando se nombra app, se afina: no "Linear" sino "Linear dashboard", "Linear navigation", "Linear project views". Duolingo: 546 usuarios con decenas de variantes ("Duolingo onboarding", "Duolingo gamification").
- **Qué funciona mejor, según el post:** preguntar por un patrón de UI concreto **referenciando cómo lo resuelven apps reales**.

**Patrón de uso observado (importante y poco intuitivo):**
&gt; Nadie escribe directamente en Mobbin MCP: toda consulta pasa primero por el cliente de IA, que decide cuándo y cómo buscar. A veces el modelo **reescribe la petición**, la expande o la parte en varias búsquedas con contexto de la conversación.

Implicación práctica: **la calidad del resultado depende tanto del cliente (Claude Code vs Cursor vs Codex) como de Mobbin.** Esto explica por qué las mismas consultas dan experiencias tan distintas entre autores — y probablemente explica la reseña de 1/5.

**Uso integrado en flujos de trabajo:** el post menciona que Mobbin se "dobla" dentro de escribir código, **abrir tickets** y **hacer design reviews**.

**Prompts (fragmentos verificados del post, no la lista completa de 30):**
- `Compare how Airbnb and Booking.com handle checkout flows`
- `Based on this brief, pull reference screens from apps solving similar problems`
- *(pegar un PRD)* `pull reference screens for every user-facing flow mentioned in it`
- `Find pull-to-refresh animation examples from social apps`
- `Pull 30 bottom sheet examples from top iOS apps`
- `Pull reference for all three from apps with strong UX`
- Ejemplos de consulta reales citados en el post: "onboarding screens from banking apps" (41 usuarios), "fintech onboarding" (14), "ai chat interface" (8)

## 5. Workflows recomendados (los cinco que preguntabas)

### 5.1 Subagente "design engineer" — el más citado
Origen: Evangeline Ng. Lógica: **como el MCP solo da capturas planas, hace falta un paso intermedio que las lea como las leería un diseñador que tiene que shipearlas**: layout, espaciado, inventario de componentes, tokens, estados de interacción, motion y *"the decision underneath the surface"*. Sin ese paso, salen resultados "vibe-coded".

Secuencia: contexto de producto/persona/objetivo → Mobbin trae referencias → **subagente descompone antes de generar** → implementación como componentes reales en rutas `/proto/v1..v3`.

Variante de João Queirós con puerta humana: investigar → **informe HTML visual** → revisión humana → construir respetando tokens.
Variante de andy en X: envolverlo en un **skill con "design guardrails"**.
Variante de Sherizan: skill `/mobbin` con análisis estructurado fijo (entradas, fricción, KYC, errores).
Hay incluso un skill público: [github.com/ddruids/mobbin-skill](https://github.com/ddruids/mobbin-skill) — genera 3–7 consultas automáticas desde un brief, agrupa hallazgos en patrones recurrentes con referencias enlazadas. Funciona con Claude Code, Cursor, Gemini CLI y Lovable.

### 5.2 Mobbin MCP + Figma MCP
Consenso claro sobre el reparto: **Mobbin = referencia externa; Figma MCP = tu design system y tus tokens.** Complementarios, no competidores (Wooldridge, TOOOLS, ChatForest).
- Demirci: PRD y wireframes en Claude Code → Mobbin ilustra → Figma MCP materializa.
- Elizabeth Alli: ciclo bidireccional auditoría → rediseño → de vuelta a Figma.
- Sherizan: Mobbin + **Figma Console MCP** para colocar y ordenar frames automáticamente, orquestado por Claude CLI.

### 5.3 Mobbin → prototipo en código
- Rutas versionadas en Next.js (`/proto/v1`, `/v2`, `/v3`) para comparar direcciones — Evangeline.
- Maquetas HTML de fidelidad media **dentro del repo** para handoff de equipo — Dianne Alter.
- Emparejar con **shadcn/ui MCP**: *"reference screenshot in, production component out"* — DeveloperToolkit.
- Regla operativa: *"make the agent look at prior art before it writes a line of UI code"*.

### 5.4 Benchmarking competitivo
- Prompt canónico: `Compare how [A] and [B] handle [flujo]`.
- Usar el metadato `app_name` de los resultados para auditorías de patrón.
- **Fijar región explícitamente** — es el fallo documentado (Sherizan).
- `search_flows` con `limit` bajo para flujos multi-paso.
- El combo Figma MCP + Mobbin MCP permite comparar tu pantalla real contra el estándar del sector en la misma sesión.

### 5.5 Marketing y landing pages
El caso con herramienta propia: **`search_sections`**. Según DeveloperToolkit, *"section-level search beats screen-level: you assemble a page from best-of-breed sections"*. Ejemplo de consulta: `pricing section with three-tier comparison table and highlighted recommended plan`.
Aplicaciones documentadas: comparar la estructura y el contenido de tu landing contra landings B2B habituales; crítica de landing pages existentes (el vídeo de daily.dev incluye crítica de páginas de curso y moodboards).
**Límite conocido:** el microcopy se recupera *"literal"* y el tono de voz sigue siendo trabajo manual. Un competidor (Gummble) vende precisamente una herramienta dedicada de búsqueda de microcopy que Mobbin no expone — fuente con conflicto de interés declarado, [gummble.com](https://gummble.com/blog/gummble-mcp-vs-mobbin-mcp).

## 7. Resumen honesto, separando hecho de opinión

**Hechos sólidos:**
1. El uso real no es generar UI: 16 de 317.427 consultas. Es un **buscador de referencia** dentro del agente.
2. El dato que devuelve es **plano** (capturas), y la previsualización inline es **baja resolución** por diseño.
3. El coste real no es el precio (10-15 $/mes) sino el **contexto**: cada pantalla es una imagen. Pedir 3–8, no 20.
4. La consulta que llega a Mobbin **la reescribe tu cliente de IA**, no tú.
5. Está en beta, de pago obligatorio, y con un hueco relevante: no lee el contenido de tus colecciones curadas.

**Mi opinión, y va en contra del tono de casi todas las fuentes:** este ecosistema de reseñas está saturado de creadores con incentivo. Once voces positivas de gente que vive de publicar sobre herramientas de IA, y una sola voz sin incentivo que dice que le empeoró los diseños. Eso no significa que Mobbin MCP sea malo — significa que **el valor está casi todo en el andamiaje que construyes alrededor** (subagente descompositor, puerta humana, tokens del DS forzados, región fijada, `limit` bajo). Sin ese andamiaje, la reseña de 1/5 es el resultado esperable, no una anomalía. Quien mejor lo usa es quien menos confía en el prompt directo: todos los casos buenos acaban en un skill o un subagente.

Para tu contexto de Ágora, lo relevante de verdad: **Mobbin es referencia externa; tu Design System es la ley.** Los dos fallos documentados que te afectarían directamente son que el primer output ignoró el design system y llegó en modo oscuro sin pedirlo, y la deriva de tokens y accesibilidad. Con la regla de "tokens por componente" y "revisar dark siempre" que ya tienes, cualquier integración tendría que pasar por una puerta de revisión antes de tocar el archivo.

## Lo que Mobbin no cubre y quién sí

Mobbin, tras lanzar *Mobbin Sites* (ago 2025), llega a apps iOS/Android/web y páginas de marketing por secciones. **Fuera de su alcance, con alternativa:**

- **Emails** — Page Flows los incluye dentro de su suscripción; **Really Good Emails** es la referencia del sector, navegación gratis, con MCP propio. Ojo al matiz: ese MCP es del *builder* RGE Studio (buscar/crear/clonar/exportar HTML de tus propios diseños), **no** búsqueda agéntica sobre la galería de inspiración. Gratis de conectar en todos los planes, OAuth, sin límites de uso.
- **Presentaciones / decks** — hueco real, sin buena solución. Slidebook.io y bestpitchdeck.com agregan decks de inversión reales; deck.gallery son 15 piezas curadas. Ninguno tiene API ni MCP y **ninguno publica tamaño de catálogo verificable**. Además son decks de *fundraising*, no de formación ni de producto: para las slides de Evolve sirven poco.
- **Branding / identidad** — **Brand New** (UnderConsideration) es el estándar, con una sección *Collected → Guidelines* que recopila manuales de marca reales. Contenido de suscripción; precio no verificado. Sin API.

Ninguno de los dos ofrece API ni MCP, así que un agente no los consume: se leen a mano.

## El MCP no oficial: `pdcolandrea/mobbin-mcp`

**Veredicto: no usarlo.** Tres razones independientes, cualquiera de ellas bastante.

1. **Está muerto.** Archivado el 15 de mayo de 2026, repositorio en solo lectura. 46 estrellas, 14 forks, 54 commits, licencia ISC. El propio autor escribe que no habrá más actualizaciones ni PRs y remite al MCP oficial de Mobbin.
2. **Cómo funcionaba.** Ingeniería inversa de los endpoints internos de Mobbin (no hay API pública en el momento de escribirlo). Exponía 10 tools (`mobbin_search_apps`, `_search_screens`, `_search_flows`, `_quick_search`, `_get_app_screens`, `_get_app_flows`, `_popular_apps`, `_list_collections`, `_get_screen_detail`, `_get_filters`). Autenticación pegando las cookies del navegador con `copy(document.cookie)`, token de sesión Supabase guardado en `~/.mobbin-mcp/auth.json`, auto-refresh contra `/auth/v1/token`.
3. **Choca de frente con los ToS de Mobbin.** Su política de uso aceptable prohíbe expresamente agregar, espejar, cachear, archivar o rehospedar contenido mediante scraper, robot, bot, spider o crawler sin consentimiento escrito previo, y prohíbe usar IA o ML para crear obras derivadas o entrenar modelos. Un MCP que consulta endpoints internos con cookies robadas de sesión es exactamente el supuesto descrito. Añade un riesgo operativo aparte: distribuir cookies de sesión de una cuenta corporativa por el equipo es una mala práctica de seguridad con o sin contrato de por medio.

No encontré en el repo ninguna advertencia legal explícita, solo el reconocimiento de la ingeniería inversa. La ausencia de advertencia no es una autorización.

## Riesgos legales y de PI al usar capturas de apps ajenas en una empresa

*Resumen prudente, no asesoría legal; para una política formal en Evolve, que lo valide alguien de legal.*

**Lo que está razonablemente tranquilo:** uso **interno y privado** como referencia. Carpeta o board con acceso restringido al equipo, cada captura con origen y fecha, etiquetada como "referencia, no producción", recortada al patrón concreto que se discute y no a la pantalla entera de marketing. Nunca conservar capturas con datos de clientes, empleados o métricas confidenciales.

**Dónde empieza el riesgo real:**

- **Redistribución.** En el momento en que la captura sale del círculo privado —blog, portfolio, deck de ventas, propuesta a cliente, galería pública, o sincronizar la carpeta de inspiración a una unidad compartida abierta— se activa el análisis completo de copyright. Tener acceso a una interfaz (incluso tras login) no es licencia para redistribuirla.
- **Idea vs expresión.** El copyright no protege *la idea* de una navegación lateral, un toast o un acordeón de temario. Sí protege la expresión concreta: un sistema de ilustración distintivo, un set de iconos propio, o una pantalla replicada tan de cerca que la nueva UI es obra derivada. El criterio operativo es "sustancialmente similar".
- **Trade dress / marca.** El aspecto global distintivo de un producto puede protegerse si es no funcional, distintivo y su imitación genera confusión. Usar logotipos ajenos para identificar el producto en una comparativa suele encajar en uso nominativo; usarlos de forma que sugiera patrocinio o afiliación, no.
- **Términos de servicio.** Independiente del copyright y más fácil de incumplir: casi todas las bibliotecas (Mobbin incluida) y muchos productos prohíben el scraping y el entrenamiento de IA sobre su contenido. Ahí el riesgo es contractual —cierre de cuenta, reclamación— y no necesitas infringir ningún derecho de autor para incurrir en él.

**Regla práctica para el equipo, que además mejora el diseño:** estudiar la referencia, escribir por qué funciona y qué trabajo resuelve, **cerrar la referencia**, y diseñar desde ese enunciado con la tipografía, el color y los componentes propios del DS. Eso resuelve a la vez el riesgo legal y el problema de acabar con pantallas que parecen de otro producto. Cuando exista press kit oficial, usarlo antes que capturar la app en vivo.

## Recomendación

1. **No sustituyas Mobbin.** Su MCP oficial ya cubre el caso de uso agéntico y su taxonomía de flujos sigue sin rival. Para MCP necesitas plan Pro; para API REST, Team.
2. **Añade Refero** si quieres un segundo MCP: es el único first-party serio además de Mobbin, y el plugin de Figma le da valor en tu flujo real. $120/año es ruido presupuestario.
3. **Añade Nicelydone** para Ágora y Atlas concretamente: pricing, onboarding, settings, billing y gestión de equipo en SaaS web es exactamente el territorio de las pantallas de administrador que te faltan, y Mobbin está más flojo ahí.
4. **Ignora Lazyweb** como biblioteca. Tiene un activo genuinamente único —el corpus de test A/B y el historial de versiones— pero es una herramienta de growth, y su material comparativo no es fuente fiable sobre terceros.
5. **Para los huecos** (decks, branding, design systems documentados) no hay nada consumible por agentes. Really Good Emails cubre email a mano; designsystems.surf y component.gallery se leen a mano. Presentaciones es un hueco de mercado sin tapar.
