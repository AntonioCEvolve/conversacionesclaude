Buena pregunta, porque es justo el caso donde Impeccable se puede pasar de frenada. La clave está en el orden.

## Lo crítico primero

En su SKILL.md hay una distinción que decide todo:

> "Refinement preserves; redesign replaces. Redesign … treats the old look as evidence and anti-reference."

Es decir: si le pides trabajo visual en un proyecto a medias **sin haber capturado antes el sistema que ya tienes**, puede concluir que estás en fase de reemplazo y tratar tu look actual como anti-referencia. Se cargaría tu dirección visual. Por eso el orden no es opcional.

## Fase 0 — diagnóstico, riesgo cero

Ninguno de estos toca un archivo:

```bash
npx impeccable detect src/
```

Detector determinista de 60 reglas, local, sin API key, sin red. Te dice qué patrones "AI-slop" hay en el código tal cual está.

Y dentro de Claude Code:

```bash
/impeccable
```

Sin argumento no ejecuta nada: lee señales del proyecto (archivos que tienes sucios en git, si hay dev server levantado, si existe DESIGN.md, hits del detector) y te propone 2-3 comandos con el motivo. Es el mejor punto de entrada para un proyecto empezado, porque razona sobre tu estado real.

## Fase 1 — capturar lo que ya existe

```bash
/impeccable init
```

Te entrevista (máx. 3 preguntas por ronda) y escribe `PRODUCT.md`: usuarios, propósito, posicionamiento, restricciones, compromisos de marca, accesibilidad. **No inventa mundo visual ni toca DESIGN.md** — está explícitamente prohibido en su flujo.

```bash
/impeccable document
```

**Este es el que no te puedes saltar.** Escribe `DESIGN.md` con el sistema visual que ya tienes: frontmatter YAML con tokens de color y tipografía extraídos de tu código, más prosa de cómo aplicarlos. Sigue el spec oficial DESIGN.md de Google Labs, así que es portable a otras herramientas. A partir de aquí, tu identidad actual es ley y no material de derribo.

## Fase 2 — mejorar

Aquí ya puedes elegir según lo que te duela:

| Comando | Qué hace |
|---|---|
| `/impeccable critique <surface>` | Crítica de diseño: jerarquía, claridad, resonancia. Genera un snapshot con score y P0/P1 |
| `/impeccable audit <surface>` | Auditoría **técnica**, no de diseño. 5 dimensiones puntuadas 0-4: a11y (WCAG AA/AAA, contraste, teclado, ARIA, semántica), rendimiento, theming… Documenta, no arregla |
| `/impeccable polish` | Lee el snapshot de `critique` como backlog y ejecuta |
| `/impeccable extract` | Consolida patrones repetidos (3+ usos) en componentes y tokens del DS |
| `/impeccable live` | Iteración en navegador, solo si hay dev server |

Ruta recomendada para algo a medias: `critique` + `audit` → lees el diagnóstico → decides → `polish`. Diagnosticar antes de tocar.

## Un aviso práctico de instalación

La instalación de ayer quedó a nivel proyecto en `~/Documents/.claude`. Eso significa que **solo la ves si abres Claude Code en `~/Documents`**. Si tu proyecto a medias está en un subdirectorio, ese directorio pasa a ser su propio project dir y no heredará la skill — los hooks apuntan a `${CLAUDE_PROJECT_DIR}/.claude/skills/impeccable/...` y no la encontrarían.

Dos salidas: instalarla también dentro de ese proyecto (`npx impeccable install`, eligiendo `project`), o pasarla a global. Si vas a usarla en varios proyectos, global sale mejor pese a que los hooks se activen en todas partes.

¿Cuál es el proyecto? Dime la ruta y lo monto: instalo donde toque, lanzo el detector y te traigo el diagnóstico antes de tocar nada.
